- 说法直白，一句话只讲一件事。

## 能改什么、不能改什么

| 能改 | 不能改 |
| --- | --- |
| 段落文字、列表项文字、表格里的说明文字 | frontmatter（`---` 之间的部分） |
| 句子顺序、合并或拆开段落 | 代码块（```` ``` ```` 之间的内容），一个字符都不能改 |
| 把长句拆短 | `<script setup>`、`<style>` 块，以及 Demo 组件标签（`<ButtonSizes />` 这类） |
| 删掉重复或空洞的话 | 行内代码（`` `labelHidden` `` 这类） |
| 小标题的措辞 | 链接地址；标题的数量和层级 |
| | `:::tip` 这类容器的种类和数量 |
| | 任何技术事实：行为、默认值、版本号、兼容性 |

觉得某处**事实**写错了：不要改，把文件名、行号和理由记进回报，总控去核对。

术语保持一致。动手前先通读整批文件，把同一个东西的不同叫法列成一张对照表，挑一个叫法统一用下去，对照表写进回报。比如「设计变量 / token / 设计令牌」「读屏 / 屏幕阅读器」「插槽 / slot」。英文技术名词照常保留原文，比如 `v-model`、Composables、SSR。

# 第 2 轮返工（总控验收第 1 轮：不通过）

## 第 1 轮哪里没过

内容核对通过了：代码、链接、结构都没动。问题在文风，**方向改反了**。

用户要的是大白话：八岁小孩都能听懂，平实、朴素。第 1 轮把原本口语化的句子改成了公文腔和翻译腔。用核对脚本 `tone.mjs` 数了一下，下面这些书面词在正文里出现的次数从 **182 次涨到了 442 次**，36 个文件里有 28 个变得更书面了：

> 若、将、均、该、其、即可、业务、无需、进行、置于、亦、针对、基于、显式、规范化、捕获、逃逸……

几个典型例子：

| 原文（更好） | 第 1 轮改成（更差） |
| --- | --- |
| 按钮去掉浏览器自带的外观 | 按钮清除浏览器自带的外观样式 |
| 如果一个按钮只有图标没有文字，读屏软件就无法知道它是做什么的 | 若交互控件仅展示图标而无可见文本，屏幕阅读器将无法准确获知其功能 |
| 防止焦点悄悄跳到背后的主页面上 | 防止焦点逃逸至背景页面 |
| 下面每一条都是升级时会碰到的变化。每条写四件事：变了什么、以前怎么写、现在怎么写、怎么改 | 下文梳理升级涉及的核心变更。按四项内容说明：变更内容、旧版写法、新版写法及迁移建议 |

原文真正的毛病只有两类，第 2 轮**只改这两类**：

1. **宣传腔**：比如「做工精细、现代好看」「随心挑选」「轻松放进去」「干净又小巧」「吵闹地念一遍」。删掉这些修饰，或者换成平实的事实。
2. **一句话塞了好几件事、读不顺**：拆成短句。

## 第 2 轮怎么做

- 从第 1 轮的结果出发，一个文件一个文件地对照 `git diff swarm-tree -- <文件>` 往下改：
  - 改后比原文更书面的句子，**换回原文**，或者改成更口语的说法。
  - 原文本来就通顺、只是被你换了同义词的句子，**一律换回原文**。
- 用词：
  - 用「如果」，不用「若」；用「把」，不用「将」；用「都」，不用「均」；用「这个」「它」，不用「该」「其」。
  - 用「不用」「不需要」，不用「无需」；用「你的项目」「你自己的样式」，不用「业务项目」「业务样式」。
  - 能用动词直接说的，就不要用「进行 + 名词」。
- 术语：第 1 轮的术语表可以保留，但要改成更口语的叫法。「读屏软件」比「屏幕阅读器」更好懂，第一次出现时写成「读屏软件（屏幕阅读器）」，后面统一叫「读屏软件」。「设计变量」也比「设计令牌」好懂，第一次出现时括号里注 token。
- `migration.md`、`changelog.md`：除了确实不通顺的句子，**其余全部换回原文**。
