# Internationalization

Strings that the components speak come from a message catalog. They are not hard-coded at every call site. The built-in locales are `en` and `zh-CN`. The type `AstryxLocale` is that pair.

Provide the locale once at the root. Descendants read it with `useAstryxLocale` and `useAstryxMessages`. If nobody provides one, the locale is `en`.

```ts
import { provideAstryxLocale } from '@astryx-vue/core/locale'

provideAstryxLocale('zh-CN')
```

`provideAstryxLocale`, `useAstryxLocale`, `useAstryxMessages`, `useLocale`, `useTranslator`, `normalizeLocale`, `loadAstryxCatalog`, and `useCollator` come from `@astryx-vue/core/locale` and are re-exported from `@astryx-vue/core`. `formatCalendarMonth` and `weekdayNames` stay on `@astryx-vue/core/locale`.

`normalizeLocale` maps `zh`, `zh-CN`, and `zh-Hans` to `zh-CN`, the built-in Simplified Chinese catalog. Every other tag keeps its region and only has its case fixed, so `en-gb` becomes `en-GB` and dates, numbers, and sorting follow that region. Component copy has two built-in catalogs, Simplified Chinese and English; `en`, `en-GB`, or `fr-FR` without `messages` all read the English one. An empty or unparseable tag becomes `en`.

## Reading the locale outside a component

Components format dates, numbers, relative times, and sort order with the locale of the nearest `InternationalizationProvider`, never `navigator.language`. Do the same in your own helpers:

```ts
import { useLocale, useTranslator } from '@astryx-vue/core/locale'

const { locale } = useLocale()
const { t } = useTranslator()

// Both follow the provider when it switches language.
const label = computed(() => new Intl.DateTimeFormat(locale.value).format(date))
const announce = () => t('@astryx.pagination.pageAnnounce', { current: 3 })
```

`t` takes an upstream `@astryx.*` key and returns the sentence for the active locale. An unknown key comes back unchanged, so a typo is easy to spot. It is safe to call from event handlers.

## Locales besides Chinese and English

Upstream Astryx ships about 30 React Intl JSON files in `packages/core/locales`, including `ja-JP`, `zh-TW`, and `ar-SA`. Those files are vendored, unchanged, under this package's `locales/` directory. They are not copied into TypeScript by hand. `loadAstryxCatalog` maps their keys onto `AstryxMessages`. Pass the result as the second argument of `provideAstryxLocale`.

Keys that do not fit a field are returned in `unmapped`, with the original sentence still attached. Nothing in the file is dropped quietly. Fields the file never fills stay in English; their paths are `fallbackFields`. Mapped keys missing from that file are `missingKeys`.

The built-in English matches upstream `en.json` word for word, and `pnpm check:i18n-catalog` keeps it that way. The built-in `zh-CN` is written here and reads more naturally than upstream `zh-CN.json`; do not replace it with that file. Use the loader for the other locales.

```ts
import { loadAstryxCatalog, provideAstryxLocale } from '@astryx-vue/core/locale'
import catalog from '@astryx-vue/core/locales/ja-JP.json'

const loaded = loadAstryxCatalog('ja-JP', catalog)
provideAstryxLocale(loaded.locale, loaded.messages)
```

`provideAstryxLocale('ja-JP')` without `messages` still formats dates and `useCollator` in Japanese, but component sentences stay in English. `zh-TW` does not silently become Simplified Chinese.

To refresh the JSON, run `node scripts/vendor-astryx-locales.mjs`. It follows the latest upstream `main`; pass a commit to reproduce an earlier fetch. The commit used is written to `locales/SOURCE.json`, and the source and license are recorded in `packages/core/THIRD_PARTY_NOTICES.md`.

Then run `pnpm check:i18n-catalog` (it is part of `pnpm check`). It checks that:

- every built-in field exists in both `en` and `zh-CN`, with the same shape;
- the built-in copy uses every upstream placeholder, and the built-in English matches upstream word for word;
- every translation in the 29 locale files parses, uses the same placeholder names and kinds (`{name}`, `number`, `plural`, `select`) as the English source, and has no stale keys;
- every upstream key is either mapped in `packages/core/src/locale/upstream/` or listed with a reason in `scripts/i18n-catalog/coverage.mjs`.

## Locale-aware comparison

`useCollator` returns an `Intl.Collator` for the active locale, wrapped in a computed. With no provider, the locale is `en`.

```ts
import { useCollator } from '@astryx-vue/core/locale'

const collator = useCollator({ numeric: true })
items.sort((a, b) => collator.value.compare(a.name, b.name))
```

`AstryxMessages` is the copy components actually read. Text that is not in that type is the `label` you passed, and it does not change with the locale.

The Chinese and English docs are two VitePress trees, `/` and `/en/`. That is the documentation language, not `provideAstryxLocale`. Component examples call `provideAstryxLocale` for the language of the page you are reading.
